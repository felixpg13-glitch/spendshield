# SpendShield Reality Test — 真实世界验证计划

> 2026-09-01 Felix 定: 我们一直在证明「写出来的东西符合自己的设计」,
> 但还没证明「这个设计在真实世界里成立」。0.8 停止无限开发, 先做真实验证。

## 为什么现在必须停

- **我们自己给自己出题**: 设计功能 → 写测试 → 攻击想到的地方 → 全绿 = 实现≈设计
- **没证明有人需要**: 有没有真实的人/团队愿意把真实钱流量交给 SpendShield?
- **过度工程化风险**: 没有 PMF 就做 enterprise infrastructure 是顺序错误
- **没面对真正攻击者**: Fuzz 是我们的攻击; 需要黑盒外部红队(拿公开 API 让 $50 变 $5000)
- **没有真实交易数据**: 壁垒 = 真实世界发生过什么, 不是我们认为该测什么

## 7 个必须记录的问题(每个场景)

1. 什么地方最有价值?
2. 什么地方最烦?
3. 哪个 Decision 错了?
4. 哪个 Policy 很难写?
5. 哪个攻击我们完全没想到?
6. 用户愿不愿意继续用?
7. 用户愿不愿意把真实支出交给它?

## 场景清单(按可落地性排序)

### 🥇 场景 1: 麦当当自动下单接入(第一个真实 Agent)
- **现状**: 麦当当系统(server.py)有真实下单/算价/出码能力, 全链路已跑通, 等上线(ACC02 重登 + source 标签 + 闲鱼上架三件套)
- **接入方式**: mcd server 的自动下单逻辑 = 真实 agent; 用 SpendShield 包一层闸门:
  - 下单 API → `shield.authorize(agent="mcd_bot", amount=成本, to="麦当劳")`
  - Policy: 日预算(账号产能)、单笔上限、商户白名单(麦当当)、审批阈值(>X 元人工确认)
  - 审计链: 每单留痕(谁/什么策略/为什么), 可追溯
- **真实价值**: 真请求、真金额(预约单可兜底)、真 agent、真 Policy
- **前置**: 麦当当上线三件套完成(这是 Felix 现金流主线, 优先级高于 SpendShield)

### 🥈 场景 2: SpendShield 自举(吃自己的狗粮)
- 把 SpendShield MCP server 部署到日常自动化里, 当「护栏」管真实脚本支出
- 候选: 麦当当 TG 告警脚本 / 日报脚本(agent 身份)过闸门; FlashNode 服务器采购决策(审批流)
- 验证: 真实工作流里 policy 好不好写、explain 清不清楚、审计够不够

### 🥉 场景 3: 外部红队挑战
- README / 社区发挑战: 「SpendShield 黑盒攻击——让一笔该 DENY 的交易变成 APPROVE」
- 提供: MCP / API / Policy 格式 / 文档; 奖励: 漏洞永久进 Corpus + 署名
- 这就是 External Red Team 的冷启动方式

### 场景 4: 开源真实试用者
- 等真实开发者 clone/安装后反馈(现有 2 星里 greekr4 是逆向开发者, 潜在高质量反馈源)
- 记录他们的第一个问题、第一个困惑、第一次放弃点

## 执行纪律

- **0.8 冻结功能开发**(bug fix / 文档 / 测试除外)
- 每个场景跑完: 7 问记录 → 进 docs/REALITY_FINDINGS.md → 有价值的进 Corpus
- 真实世界打回来 = 好事(开始积累别人复制不了的资产)
- 飞轮: 更多用户 → 更多真实交易 → 更多异常 → 更多攻击案例 → 更多 Policy patterns → 更多 Regression → 更安全 → 更值得信任 → 更多用户
