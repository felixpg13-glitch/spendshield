# SpendShield × x402

## Problem
x402 quotes and settles machine payments; applications using x402 may want an independent
authorization layer (budget, recipient policy, approval) around payment execution.

## Architecture
```text
client side:   agent → SpendShield.authorize → ALLOW → x402 submit (quote → sign → settle)
server side:   paid resource → paywall guard (budget/approval/audit) → settle
```

## 20-line integration
```python
from spendshield.adapters.x402 import X402PaywallGuard, protect_x402_payment

guard = SpendShield(budget=50, dry_run=True)          # your policy
pw = X402PaywallGuard(guard, action_prefix="x402")

# server: wrap a paid resource (before settlement)
ok = pw.authorize_resource("weather-api", price="0.01",
                           asset="USDC", pay_to="0x...")

# client: gate before submitting payment
protect_x402_payment(guard, amount=0.01, to="weather-api.example.com",
                     agent="research_bot")
```

## Enforcement
- Same YAML policy as any rail; budget consumption atomic at decision time.
- Signed single-use grant consumed by the execution path (no grant → no settle).

## Proof
- Adapter: `spendshield/adapters/x402.py` (module docstring shows both shapes).
- Rail-agnostic proof: `examples/three_channel_demo.py` — same policy across x402/Stripe/Alipay, zero policy changes.
- Concept page: [x402 Spending Limits](https://felixpg13-glitch.github.io/spendshield/x402-spending-limits/)

## Limitations
- x402 itself is untouched (by design — policy lives outside the protocol).
- Facilitator/settlement flows are external; SpendShield gates client & paywall sides only.
- Adapter targets x402 buyer + paywall patterns; MPP/AP2 adapters are future entries (see cookbook index).
